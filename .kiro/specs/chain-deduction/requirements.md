# 要件定義書 — chain-deduction（分岐型連鎖推理）

## 概要

**コンセプト:**  
現行の「証拠4つ→7択1問→結果」フローを廃止し、分岐型の推理ツリーに刷新する。プレイヤーは証拠を読みながら7択問題に次々と答え、**選択肢によって次の問題が変わる**（分岐）。一度選んだら戻れない。全ブランチを辿り終えた（または時間切れになった）後、自分がいくつの「課題」を解決できたかが一括開示される。

**現行フローとの主な差分:**

| 項目 | 現行 | 新規 |
|------|------|------|
| 問題数 | 1問 | 分岐型ツリー（目安 5〜12問） |
| 分岐 | なし | 選択肢ごとに次の問題が変わる |
| 後戻り | ―（1問だけ） | 不可（選んだら確定） |
| 正誤フィードバック | 即時 | 全問終了後に一括開示 |
| 最終指標 | 判決ラベル | 「課題解決数 X / Y」 |
| 結果決定 | プレイヤーが直接選ぶ | 解決した課題パターンから自動決定 |

---

## 要件

### 要件 1: 分岐型推理ステップのデータ構造

**目的:** 選択肢ごとに次の問題IDが異なる「分岐調査ツリー」を定義できるデータ構造を導入する。

#### 受入基準

1. `StepChoice` リソースは以下のフィールドを持つ：選択肢キー・表示ラベル（英語・日本語）・選択後に遷移する次のステップID（空文字 = ブランチ終端）・解決する課題ID（空文字 = 課題解決なし）。
2. `InvestigationStep` リソースは以下のフィールドを持つ：ステップID・質問文（英語・日本語）・質問タイプ（`CODE` / `LOG` / `NETWORK` / `DEDUCTION`）・コードブロック表示フラグ・選択肢配列（7件固定）・このステップに到達したとき開示される証拠ID（空文字 = 追加なし）。
3. `CaseIssue` リソースは以下のフィールドを持つ：課題ID・課題説明（英語・日本語）。
4. `OutcomeRule` リソースは以下のフィールドを持つ：最低解決課題数・必須課題IDリスト（全て解決されている必要がある）・対応するアウトカムキー。
5. `CaseData` は `verdict_choices` を廃止し、以下を追加する：`entry_step_id`（ツリーの起点ステップID）・`investigation_steps: Array[InvestigationStep]`・`resolvable_issues: Array[CaseIssue]`・`outcome_rules: Array[OutcomeRule]`。
6. `CaseData.validate()` は `investigation_steps` が1件以上かつ `entry_step_id` が有効なステップIDを参照している場合に有効とし、旧来の証拠件数4件固定制約・`verdict_choices` 制約を撤廃する。

---

### 要件 2: 後戻り不可の分岐進行

**目的:** プレイヤーが一度選択したら取り消しできない、緊張感のある推理進行を実現する。

#### 受入基準

1. When プレイヤーが選択肢を確定したとき、チェーン推理システムは選択を記録し、該当 `StepChoice.next_step_id` が示す次のステップへ進む。前のステップへ戻る手段を一切提供しない。
2. When プレイヤーが選択肢を確定したとき、`StepChoice.resolves_issue_id` が設定されている場合、チェーン推理システムは該当課題IDを「解決済み」として記録する。
3. When 次のステップIDが空文字（ブランチ終端）のとき、チェーン推理システムはそのブランチを終了し、チェーンレビュー画面へ遷移する。
4. While プレイヤーがステップを回答中のとき、チェーン推理システムは Escape キーをポーズ専用とし、前ステップへの移動には使用できない。
5. If タイムリミットが切れたとき、チェーン推理システムは未回答の現在ステップを「タイムアウト」として記録し、チェーンレビュー画面へ遷移する。

---

### 要件 3: 証拠の段階的開示

**目的:** ステップ到達時に新たな証拠が開示されることで、プレイヤーの選択が調査の深度に影響を与える。

#### 受入基準

1. ゲーム開始時（最初のステップ到達時）、チェーン推理システムは `CaseData.evidence` 内の初期証拠を全て開示する。
2. When プレイヤーが次のステップへ進んだとき、次のステップの `reveals_evidence_id` が設定されている場合、チェーン推理システムは証拠パネルに該当証拠を追加表示する。
3. While プレイヤーがステップを回答中のとき、証拠パネルには到達済みステップが開示したすべての証拠が常に参照可能な状態で表示される。

---

### 要件 4: チェーンレビュー画面

**目的:** 全ブランチ終了後に、辿ったパスの選択と課題解決結果を一括で可視化する。

#### 受入基準

1. チェーンレビュー画面は訪問した全ステップについて「質問概要・プレイヤーの選択ラベル・解決した課題ID（あれば）」を時系列で一覧表示する。
2. チェーンレビュー画面は「X / Y ISSUES IDENTIFIED」（X: 解決済み課題数、Y: ケース全体の課題数）を目立つ形で表示する。
3. When チェーンレビュー画面を表示するとき、システムは `outcome_rules` を順序通りに評価し、最初に条件を満たしたルールの `outcome_key` をアウトカムとして決定する。
4. どの `outcome_rules` にも一致しない場合、チェーン推理システムは `insufficient` アウトカムを適用する。
5. チェーンレビュー画面は「[ VERDICT ]」ボタンを提供し、プレイヤーが押したときアウトカム画面へ遷移する。
6. チェーンレビュー画面はサイバーパンク端末の美術方針（暗色背景・緑のモノスペーステキスト）を維持し、課題を解決したステップは緑色・解決しなかったステップは暗色・タイムアウトは赤色で表示する。

---

### 要件 5: アウトカム決定ロジック

**目的:** 課題解決パターン（何を・どれだけ解決したか）に基づいて複数のエンディングを決定する。

#### 受入基準

1. `OutcomeRule` の評価は配列の先頭から順に行い、最初に条件を満たしたルールを採用する。
2. 各 `OutcomeRule` は最低解決課題数と必須課題IDリストの両方を満たす場合に条件一致とする。
3. `CaseData.outcomes` は `outcome_rules` で参照される全 `outcome_key` のアウトカムデータを持つ。
4. アウトカム画面は「YOUR VERDICT」ラベルの代わりに「ISSUES RESOLVED: X / Y」を表示し、アウトカムキーに対応するナラティブを表示する。

---

### 要件 6: 問題タイプの多様性とシナリオ構成

**目的:** コード解析・ログ読解・ネットワーク分析・論理的推理を組み合わせた技術者向けシナリオを実現する。

#### 受入基準

1. 1ケースの `investigation_steps` は `CODE`・`LOG`・`NETWORK`・`DEDUCTION` の4タイプを各1問以上含む。
2. `CODE` タイプの問題はコードスニペットを問題文に埋め込み、「どの行が問題か」「バグの種別」などプログラミング知識を問う形式とする。
3. `DEDUCTION` タイプの問題は複数の証拠を横断した論理的推論を問う形式とし、コード読解なしでも解答の可能性がある。
4. `LOG` タイプの問題はタイムスタンプ付きログを読み解いてタイムラインの矛盾・異常パターンを検出する形式とする。
5. 各ステップの選択肢7件のうち課題を解決できる選択肢は1件以上設け、残りは「もっともらしいが解決しない」デコイとして設計する。
6. ケース001（ASTRA-7事件）用に分岐ツリーを含む `case_001.tres` を再設計する。ツリーは `CODE`・`LOG`・`NETWORK`・`DEDUCTION` を含み、解決可能な課題を5件以上定義する。

---

### 要件 7: キーボード・マウス操作

**目的:** 分岐推理チェーンの全操作をキーボードとマウスの両方でサポートする。

#### 受入基準

1. While 推理ステップ画面が表示中のとき、プレイヤーは ↑/↓ キーで選択肢を移動し、Enter / Space で確定できる。
2. When プレイヤーがマウスで選択肢をクリックしたとき、システムはその選択肢を確定して次のステップへ進む。
3. While チェーンレビュー画面が表示中のとき、プレイヤーは Enter / Space またはマウスクリックで [ VERDICT ] ボタンを押してアウトカム画面へ進める。
